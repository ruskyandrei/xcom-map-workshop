# EXP-29: starting the game straight in a battle on a map

Date: 9 November 2026. Can a map be tested without starting a campaign and without changing the game's first
mission? Then: try it the way that needs no Steam launch option (`-EXEC=`) and, if it works, have the editor's
Install as intro map start a map that way instead.

## Question

Until now a build was tested as the first mission of a new campaign: the editor rewrote the one `DefaultMaps.ini`
record LWR's first mission plays (EXP-03), and a new campaign was started each time.

Read from the exe and the scripts beforehand (no run):
- the engine takes `-EXEC=<file>` anywhere on the command line and has its first local player run `exec <file>` once
  it is up (the exe, 0xA7AFD0). `exec` reads the file from `..\..\Binaries\` unless the name has `Binaries` in it
  (0x825820: the strings `Binaries` and `..\..\Binaries\`), so from `XEW\Binaries`;
- the console's `open <Map>` loads a map. `XComGameInfo.SetGameType` makes any map not named Shell or Command1 a
  tactical game, and `XComTacticalGame.m_bLoadingFromShell` is true unless the URL says `LoadingFromStrategy`: the
  battle is then built from the profile's developer squad (`XComTacticalGRI.InitBattle`), Firaxis's own path
  (`XComAutoTestManager`, and the developer shell still in `XComUIShell_SF.upk`, which nothing opens);
- the map's streams come from the first `DefaultMaps.ini` record whose Name is the loaded map
  (`GetCurrentMapMetaData`, 0xBE4900), so a variant needs a record of its own, and a map of the game's needs nothing.

What only the game could say:
1. Does `-EXEC=` reach the game through Steam, its stub and its launcher, with no launch option set?
2. Does a battle started this way run under LWR, whose scripts never mention it?
3. Does a variant with a record of its own, out of rotation, get its patch, landing and landing zones?

## Runs

All in the lab copy, started through Steam, the launcher's Enemy Within clicked by `click_launcher.ps1`. The lab's
Steam launch option (the wrapper) stayed as it is: it only adds `-nohomedir` and `-forcelogflush` there.

**Run 1: `steam.exe -applaunch 200510 -EXEC=exp29-bar.txt`, the file holding `open URB_Bar`.**
- Steam handed the argument on with no question asked, and the launcher handed it to the game:
  `Command line: -FROMLAUNCHER -EXEC=exp29-bar.txt -nostartupmovies -nohomedir -forcelogflush -LANGUAGE=INT`.
- 4.4 s after the game started: `Execing ..\..\Binaries\exp29-bar.txt`, `LoadMap: URB_Bar`, `Game class is
  'XComTacticalGame'`, the record's streams (`CIN_DropshipIntros`, `patch_bar`, `patch_hide_randomized_objects`),
  LWR's mutators, pods and meld. The Skyranger's landing played, and the battle stood at turn 1. Soldiers were
  moved.
- **The squad was wrong:** four unit flags and no bodies (`EXP-29-run1-no-bodies.png`); two of the four had no weapon
  (`Accessed None 'm_kInventory'`, `'ActiveWeapon'`).
  - No bodies: nothing on this path asks for the soldiers' content. In a campaign the base does before the mission,
    and Firaxis's shell did in its loadout screen (`UISinglePlayerLoadout.RequestContent`) or its auto-test
    (`XComAutoTestManager.RequestUnitContent`), before `open`.
  - No weapons: the game's developer squad (`XComOnlineProfileSettings.LoadoutSlots`) is two MEC troopers, a heavy
    and a support, and under Long War the MECs' gear comes out empty.

**Run 2: `open URB_Bar?SquadContent=restart` after `set XComOnlineProfileSettings LoadoutSlots (…)`.** No change.
`XGBattle`'s `Starting` state loads the soldiers' content when the URL has "restart" in it, but the battle's
description doesn't exist yet at that point on this path (`Accessed None 'm_kDesc'`). And the squad is built from
`LoadoutSlots` when the game starts, before the file runs.

**Run 3: `set XComContentManager bAllowJITLoad True`, with `get` and `getall` to see what the commands do.**
- `set`, `get` and `getall` all work in the shipped game. `getall XComOnlineProfileSettings m_aSoldiers` printed the
  four soldiers as text, which is the form a `set` takes.
- With `bAllowJITLoad` the content manager loads what is asked for and missing (`WARNING: JIT Loading
  Soldier_MaleCarapace.ARC_MaleCarapace`, the weapons, the aliens'): the heavy and the support had bodies. The MECs
  still had none.

**Run 4: a squad of six by item names, and the profile settings made afresh.** `set … LoadoutSlots` with six
slots, then `set XComEngine XComProfileSettings None`, so that `InitBattle` builds the squad again from the slots.
Six soldiers with bodies and weapons (`EXP-29-run4-squad.png`), generated by the game (LWR's names and numbers).

**Run 5: the same on `URB_BarBlank`. The game stopped while starting,** before the file ran: `Runaway loop detected`
in `XComContentManager.GetPossibleVoices`, called from the squad's making in the shell. Two causes, both this
experiment's:
- **`set` saves.** After setting a property the engine saves the class's config (`GlobalSetProperty` ends with the
  class default object's `SaveConfig`). Runs 2 to 4 had written `bAllowJITLoad=True` and the six `LoadoutSlots` into
  the lab's `XComContent.ini`, and rewritten the content manager's whole section in the engine's own layout.
- **Long War's voice picker can run away.** With six slots saved, the game built six soldiers at its next start,
  and the fifth or sixth, of a random country, sent `GetPossibleVoices` round for ever: its loop keeps its counter
  in the list it also removes voices from. Four slots build the same four soldiers at every start, which is why the
  game's own squad never meets it.
The lab's `XComContent.ini` was deleted and the game made it afresh from `DefaultContent.ini`.

**Run 6: the squad written straight into `m_aSoldiers`, on `URB_BarBlank`.** `set XComOnlineProfileSettings
m_aSoldiers ((kChar=(…),kSoldier=(…),…),…)`: six soldiers in the text form run 3 printed, with LWR's item numbers
(`XGGameData.EItemType` in LWR's scripts: pistol 2, rifle 3, shotgun 4, machine gun 5, sniper rifle 6, rocket launcher
7, kevlar 59, carapace 60, medikit 69, frag grenade 81, needle grenade 87). No soldier is generated, so the voice picker
isn't called, and `LoadoutSlots` stays the game's own.
- The six on the blank map (`EXP-29-run6-variant.png`), named and armed as written.
- `URB_BarBlank` is EXP-08's variant, with a record of its own that is out of rotation: its streams were its
  record's (`patch_exp08blank` among them) and LWR's landing code named it (`URB_BarBlank (EXP-08 blank map) |0`).
- What the two `set`s left in `XComContent.ini`: `bAllowJITLoad=True`, the game's own four `LoadoutSlots` written
  out, and the content manager's section in the engine's layout. The game started the normal way afterwards.

**Run 7: through the editor.** A test server (port 8790) with the new Play in game, asked to play the project
"EXP-26 lights" (its last build, baked):
- the editor added the variant's record after Bar's (line 6: `Name="URB_Bar_Exp26Lights_26a0"`,
  `DisplayName="URB_Bar_Exp26Lights_26a0 (XCOM Map Workshop) |0"`, `bInRotation=False`), wrote
  `XEW\Binaries\XComMapWorkshop-play.txt`, kept both `XComContent.ini` files aside (the lab's own and the one under
  Documents, which a game without `-nohomedir` uses) and started Steam;
- the game: `Execing ..\..\Binaries\XComMapWorkshop-play.txt`, `LoadMap: URB_Bar_Exp26Lights_26a0`, streaming the
  variant's own landing intro (`CIN_DropshipIntros_URB_Bar_Exp26Lights_26a0`), `patch_bar` and
  `patch_hide_randomized_objects`; the squad beside the Skyranger's place (`EXP-29-run7-editor.png`), the project's
  lights on the bar;
- during the play the lab's `XComContent.ini` had five `set` lines in it; within a few seconds of the game closing
  the editor's watch had put the file back (same hash as before the play, `0fa5d76f…`), and the Documents one was
  never touched;
- Remove from game took the record, the commands file and the files of an earlier install out; `DefaultMaps.ini`
  had its hash from before the play (`01d012fc…`).

## Answers

1. Yes. `steam.exe -applaunch 200510 -EXEC=<file>` needs nothing set in Steam; the launcher still wants its click.
2. Yes, with two console commands for the squad: the content loaded on demand, and the soldiers written out. The
   battle is a plain one: the map's own landing, aliens of the game's choosing, six squaddies. About half a minute
   from the launcher click to the first turn (run 6's log: the map loaded 4 s after the game started, the squad stood
   at 23 s), most of it the landing.
3. Yes: streams, the variant's own landing intro and LWR's landing zones, from a record out of rotation.

Findings register: F-72 (the path), F-73 (`set` saves the config), F-74 (the squad), F-75 (the voice picker).

## Not known

- Play beyond the first moves: a whole battle, its end screen, saving and loading in it, and whether the game writes
  the profile (`profile.bin`) at any point. None of the seven runs wrote a save or the profile; the longest was about
  eight minutes with a few moves. On this path the profile is the game's default one, never read from disk, so a
  write would replace the user's settings with defaults.
- Missions with a script of their own (bomb, rescue, the council's): the battle takes its kind from the record, but
  nothing of a campaign is behind it. The editor writes a variant's record as an abduction whatever the base map's
  kind (as the intro slot did, EXP-14), which wasn't played on this path: every run was on the Bar. A map of the
  game's opened from a record of another kind (Temple Ship's `eMission_Final`) wasn't tried either.
- Plain Enemy Within, and Long War without Rebalance: no install here. The editor sets no squad on plain EW (its item
  numbers aren't LWR's) and takes Long War's to be LWR's.
- A game folder outside a Steam library, started by its own `XComEW.exe`: not tried.
- The lab's Steam launch option was set during every run. It only adds arguments after Steam's own, so Steam's
  handing on of `-EXEC=` is shown; a Steam with no launch option at all wasn't run.
